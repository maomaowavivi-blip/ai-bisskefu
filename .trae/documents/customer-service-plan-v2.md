## 一、核心架构调整：从 SaaS 到单租户部署

### 1.1 为什么单租户？

| SaaS 模式     | 单租户独立部署 ✅                |
| ----------- | ------------------------ |
| 多客户共享数据库    | **每个客户独立 VPS + 独立数据库**   |
| 一个故障影响所有客户  | 故障隔离，互不影响                |
| 需要复杂的租户隔离代码 | 代码天然隔离，无需 enterprise\_id |
| 升级需要灰度      | 逐个客户升级，可回滚               |
| 客户对数据安全有顾虑  | 数据完全在客户自己的服务器            |

### 1.2 部署架构

```
┌─────────────────────────────────────────────────────────┐
│                    客户管理端（可选）                      │
│         记录客户 VPS 信息、版本、状态、续费               │
└──────────┬────────────────────────────────┬────────────┘
           │ SSH/密钥                         │
           ▼                                  ▼
   ┌──────────────┐                  ┌──────────────┐
   │  客户A VPS    │                  │  客户B VPS    │
   │  CentOS 7+   │                  │  CentOS 7+   │
   │  宝塔面板     │    同一套代码      │  宝塔面板     │
   │  Nginx       │  ←─────────────→  │  Nginx       │
   │  PHP 8.0     │   各自独立部署      │  PHP 8.0     │
   │  MySQL 5.7   │                  │  MySQL 5.7    │
   │  独立域名     │                  │  独立域名     │
   │  独立数据库   │                  │  独立数据库    │
   └──────────────┘                  └──────────────┘
```

### 1.3 部署脚本化

```bash
# deploy.sh - 一键部署到新客户 VPS
./deploy.sh --domain=kefu.customer.com \
            --vps=123.45.67.89 \
            --db-password=xxx \
            --admin-email=admin@customer.com
```

部署脚本自动完成：

1. 推送代码到服务器
2. 创建 Nginx 配置 + SSL 证书（Let's Encrypt）
3. 初始化 MySQL 数据库 + 导入表结构
4. 创建管理员账号
5. 配置定时任务（日志清理、备份）

## 二、微信生态接入方案（轻量级）

### 2.1 接入矩阵：四种客户类型，四种方案

大多数企业没有能力修改小程序源码，所以必须提供「不需要修改小程序」的接入方式。

```
┌─────────────────────────────────────────────────────────────────┐
│                    接入方式优先级矩阵                             │
├──────────────┬──────────────────┬────────────────┬──────────────┤
│              │  有公众号         │  无公众号       │  有官网       │
├──────────────┼──────────────────┼────────────────┼──────────────┤
│ 有自研小程序  │ 方案A+B(双入口)   │ 方案B(优先)     │ 方案D(补充)   │
│ 租用SaaS小程序 │ 方案A(最佳实践)   │ 方案C(唯一选择)  │ 方案D(补充)   │
│ 无小程序      │ 方案A(唯一选择)   │ 方案D(唯一选择)  │ 方案D(优先)   │
└──────────────┴──────────────────┴────────────────┴──────────────┘
```

### 2.2 方案A：公众号菜单链接（⭐ 首推 - 最简单）

**适用场景**：客户有微信公众号（服务号或认证订阅号）

**原理**：微信公众号后台可以直接添加外部链接菜单，**无需任何开发**

**配置步骤**（客户自助完成，5分钟）：

```
公众号后台 → 菜单管理 → 添加菜单
  → 菜单名称：「在线客服」或「AI助手」
  → 菜单类型：跳转网页
  → 页面地址：https://kefu.customer.com/chat
  → 保存发布
```

**优势**：

* ✅ **零代码** - 客户自己在公众号后台点几下就搞定

* ✅ **无域名白名单** - 公众号跳转外部H5不需要配置业务域名

* ✅ **无需客户开发** - 不需要改动小程序

* ✅ **微信内置浏览器** - H5 在微信内打开体验流畅

**推广话术**：

> "您只需要在公众号后台添加一个菜单，指向我们给您的链接，您的粉丝就能直接跟AI客服聊天了，整个过程不需要任何技术人员参与。"

### 2.3 方案B：小程序 WebView 嵌入（需客户配合）

**适用场景**：客户有自研小程序，能修改源码或联系 SaaS 平台配置

**方式 B1：源码级（自研小程序）**
客户在小程序添加一个页面，使用 WebView 组件：

```html
<!-- 客户小程序 - 新增 chat.wxml 页面 -->
<web-view src="https://kefu.customer.com/chat?openid={{openid}}"></web-view>
```

**客户需要做**：

1. 小程序后台配置「业务域名」（将 `kefu.customer.com` 加入白名单）
2. 在 WebView 页面 URL 中传入用户标识

**方式 B2：SaaS 租用小程序**
联系 SaaS 提供商（有赞/微盟等）添加业务域名：

```
客户 → SaaS客服 → 提供域名 + 校验文件 → SaaS配置 → 完成
```

**成功率评估**：

* 有赞/微盟：中高（付费商家通常支持）

* 小型SaaS：不一定支持

* 纯模板小程序：基本不支持

### 2.4 方案C：客服消息转发（⭐ 第二推荐 - 无需改代码）

**适用场景**：客户的小程序完全无法修改（纯租用模板）

**原理**：利用微信自带的「客服消息」功能，后端对接微信客服消息 API

```
用户在小程序点击「客服」按钮
        ↓
微信客服消息系统
        ↓ (Webhook 推送)
你的 AI 后端 (接收消息 → AI 回复 → 调用客服消息 API 发送)
        ↓
用户收到客服回复（在微信「服务通知」或小程序客服消息中）
```

**客户需要做**：

1. 在小程序管理后台开启「客服消息」
2. 配置客服消息推送 URL 指向你的服务器
3. 无需修改任何小程序代码

**优势**：

* ✅ **零修改小程序** - 租用 SaaS 的客户也能用

* ✅ **原生体验** - 用户通过小程序自带客服入口进入

* ✅ **微信官方通道** - 稳定可靠

**缺点**：

* ⚠️ 被动回复（用户主动发消息后才能回复）

* ⚠️ 消息格式有限制（不能发富文本卡片）

* ⚠️ 响应有时间窗口限制

### 2.5 方案D：官网 iframe 嵌入

**适用场景**：客户有企业官网

```html
<!-- 客户在官网底部嵌入 -->
<script src="https://kefu.customer.com/sdk/chat-widget.js"></script>
<script>
  ChatWidget.init({
    position: 'bottom-right',
    themeColor: '#6C5CE7',
    companyName: 'XX企业'
  });
</script>
```

**客户需要做**：

1. 在官网底部粘贴一行 JS 代码
2. 无需其他配置

## 三、验证流程（极简设计）

### 3.1 原则

```
┌─────────────────────────────────────────────────────┐
│  不记忆、不追踪、不建CRM                              │
│  每次查询都是独立的：订单号 + SMS验证码 → 查一次清一次  │
│  客服AI只回答：知识库内容 + 本次查询结果                │
└─────────────────────────────────────────────────────┘
```

### 3.2 两种模式

| 模式 | 做什么 | 需要验证？ |
|------|--------|:---------:|
| **闲聊模式** | 打招呼、问产品知识、闲聊 | ❌ 不需要 |
| **查询模式** | 查订单状态、物流信息 | ✅ 必须 SMS 验证 |

用户打开聊天窗就是闲聊模式，需要查订单时，引导进行 SMS 验证。

### 3.3 一条完整流程

```
用户: "我的快递到哪了？"
        ↓
AI: "亲，查订单需要验证您的身份~
     请提供您的 **订单号** 和 **手机号**，
     我给您发验证码~"
        ↓
用户: "ORD1234567890，13812345678"
        ↓
verify.php：
  ① 手机号脱敏 → 138****5678
  ② 频率检查（同一IP 1分钟内最多发3次验证码）
  ③ 调用短信API发送6位验证码
  ④ 记录日志（手机号只留哈希，验证码只留哈希）
        ↓
用户手机收到短信: 【XX客服】您的验证码是 385792，5分钟内有效
        ↓
用户: "385792"
        ↓
verify.php：
  ① 验证码校验（哈希比对）
  ② 验证通过 → 记录已验证
  ③ 调用企业订单 API（传订单号 + 手机号）
  ④ 企业 API 验证 order_no + phone 是否匹配
  ⑤ 匹配 → 返回订单数据
        ↓
AI: "查到啦~ 您的【夏季连衣裙】已发货，
     顺丰单号 SF1234567890，预计明天到~ 😊"
```

**关键规则**：
- 每次查订单都要走一遍验证（不记住你是谁）
- 验证码 5 分钟有效，过期重发
- 同一手机号一天最多收 5 条验证码
- 验证码明文不存数据库（只存哈希）
- 手机号明文不存数据库（只存哈希 + 脱敏显示）

### 3.4 数据库

不需要 visitors 表、不需要记忆表、不需要摘要表。只需要一张日志表做频率限制和审计：

```sql
-- 短信验证日志（频率限制 + 审计）
CREATE TABLE sms_verify_logs (
    id INT AUTO_INCREMENT PRIMARY KEY,
    phone_hash VARCHAR(64) NOT NULL,             -- 手机号SHA256哈希
    phone_mask VARCHAR(20) NOT NULL,             -- 脱敏显示 138****5678
    otp_hash VARCHAR(64) NOT NULL,               -- 验证码SHA256哈希
    session_id VARCHAR(64) NOT NULL,              -- 当前会话ID
    source_ip VARCHAR(45) DEFAULT NULL,           -- 请求IP
    status TINYINT DEFAULT 0,                    -- 0=已发送 1=已验证 2=已过期
    expires_at DATETIME NOT NULL,                -- 5分钟有效期
    verified_at DATETIME DEFAULT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_phone_hash (phone_hash),
    INDEX idx_source_ip (source_ip),
    INDEX idx_created (created_at)
);

-- 对话记录（仅做历史查看，不做记忆注入）
CREATE TABLE chat_logs (
    id INT AUTO_INCREMENT PRIMARY KEY,
    session_id VARCHAR(64) NOT NULL,
    channel VARCHAR(20) DEFAULT 'web',           -- web / wechat_mp / wechat_msg
    role VARCHAR(10) NOT NULL,                    -- user / assistant
    content TEXT NOT NULL,
    has_verified TINYINT DEFAULT 0,               -- 本轮是否验证过
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_session (session_id),
    INDEX idx_created (created_at)
);
```

## 四、安全验证体系（核心安全设计）

### 4.1 核心原则：AI 不碰敏感数据

订单信息极其私密，**AI 模型绝对不能直接接触原始订单数据**。整个系统的安全架构建立在分层隔离上：

```
用户提出问题
    │
    ├── 知识库类（产品介绍/价格/营业时间/退换货政策...）
    │   → AI 直接回答（知识库内容本身就是公开信息）
    │   → ✅ 不需要验证
    │
    └── 订单类（订单状态/物流/退款进度...）
        → AI 引导用户提供验证信息
        → 后端执行验证 + 调用订单API
        → AI 只拿到脱敏后的结果摘要
        → 🔒 必须验证
```

### 4.2 权限分级

| 等级 | 内容 | 示例 | AI可回答？ | 需要验证？ |
|------|------|------|-----------|-----------|
| **L0 公开** | 知识库FAQ、产品介绍 | "这个多少钱？""怎么退款？" | ✅ 直接回答 | ❌ 不需要 |
| **L1 低敏感** | 公开活动、营业时间 | "你们几点开门？" | ✅ 直接回答 | ❌ 不需要 |
| **L2 需验证** | 订单状态、物流信息 | "我的订单到哪了？" | ✅ 但需引导验证 | ✅ 订单号+手机号 |
| **L3 高敏感** | 收货地址、退款到账号 | "帮我改地址" | ❌ 需升级验证 | ✅ SMS验证码 |
| **L4 人工处理** | 资金纠纷、复杂客诉 | "我要投诉赔偿" | ❌ 转人工 | ⭐ 转人工 |

### 4.3 订单验证流程（三档强度递增）

#### 第一档：订单号 + 手机号（日常查询）

```
用户: "我的订单到哪了？"
        │
AI: "亲，为了您的隐私安全，请提供您的订单号和下单手机号，
     我帮您查一下~ 😊"
        │
用户: "订单号是 ORD20260512，手机是 13812345678"
        │
        ▼
后端验证层（AI 不参与验证判断）：
  1. 频率检查（同一IP/手机号 1分钟内最多查3次）
  2. 调用企业订单API验证 order_no + phone 是否匹配
  3. 匹配 → 获取订单数据 → 脱敏处理
  4. 不匹配 → 返回"信息不匹配，请确认后重试"
        │
        ▼
AI 只拿到脱敏后的结果：
  ✅ 成功: "查询到您的订单【夏季连衣裙】，已发货，
            物流单号 SF1234567890，预计明天送达~"
  ❌ 失败: "订单号和手机号不匹配，您再检查一下？
            或者您可以在「我的订单」页面直接查看~"
```

**关键设计**：
- AI 模型**看不到完整的订单号和手机号**，验证逻辑完全在后端
- AI 只收到"通过 → 返回摘要"或"不通过 → 提示重试"的结果
- 同一 IP / 手机号连续验证失败 5 次，锁定 15 分钟防止暴力猜测

#### 第二档：SMS 验证码升级（敏感操作）

```
用户: "我要改收货地址"
        │
AI: "修改地址需要更严格的验证，我给您手机发一个验证码"
        │
后端发送短信验证码 → 用户手机收到 6 位验证码
        │
用户: "验证码是 385792"
        │
后端验证 OTP（AI 不参与验证判断）
  → 验证通过 → 允许修改地址
  → 验证失败 → 提示重试
        │
💡 安全措施：验证码不在 chat_logs 表中持久化存储
```

#### 第三档：转人工（复杂/高敏感）

```
AI: "这个问题比较特殊，我帮您转接人工客服处理~
     转接中，请稍候..."
```

### 4.4 数据脱敏层

订单 API 返回的原始数据，在进入 PromptEngine 之前必须脱敏：

```php
function desensitizeOrderData(array $rawOrder): array {
    return [
        'status'       => $rawOrder['status'],              // "已发货" - 正常
        'product_name' => $rawOrder['product_name'],          // "夏季连衣裙" - 正常
        'price'        => '***',                               // 金额脱敏
        'phone'        => '138****5678',                       // 中间四位隐藏
        'address'      => mb_substr($rawOrder['address'], 0, 6) . '****',
        'tracking_no'  => $rawOrder['tracking_no'] ?? '暂无',  // 物流单号可选显示
    ];
}
```

### 4.5 频率限制和异常检测

基于 IP 和手机号哈希进行频率限制（不追踪用户身份）：

```php
function verifyRateCheck(PDO $db, string $ip, string $phoneHash): void {
    // 同一IP每分钟最多发3次验证码
    $stmt = $db->prepare('SELECT COUNT(*) FROM sms_verify_logs 
        WHERE source_ip = ? AND created_at >= DATE_SUB(NOW(), INTERVAL 1 MINUTE)');
    $stmt->execute([$ip]);
    if (intval($stmt->fetchColumn() ?: 0) >= 3) {
        fail('发送过于频繁，请1分钟后再试', 429);
    }
    
    // 同一手机号一天最多5条
    $stmt = $db->prepare('SELECT COUNT(*) FROM sms_verify_logs 
        WHERE phone_hash = ? AND created_at >= DATE_SUB(NOW(), INTERVAL 1 DAY)');
    $stmt->execute([$phoneHash]);
    if (intval($stmt->fetchColumn() ?: 0) >= 5) {
        fail('该手机号今天已达上限，请明天再试', 429);
    }
    
    // 连续失败5次锁定15分钟
    $stmt = $db->prepare('SELECT COUNT(*) FROM sms_verify_logs 
        WHERE source_ip = ? AND status = 0 
        AND created_at >= DATE_SUB(NOW(), INTERVAL 15 MINUTE)');
    $stmt->execute([$ip]);
    if (intval($stmt->fetchColumn() ?: 0) >= 5) {
        fail('验证失败次数过多，请15分钟后再试', 429);
    }
}
```

## 五、通用订单/信息查询 API 适配器（核心设计）

### 5.1 设计理念：适配器模式

不同行业返回的数据完全不同，不能写死格式。所以设计思路是：

```
我们定义标准接口规范 ← 企业按规范实现API → 我们调用 → 数据给AI → AI自然呈现
         ↓                          ↓                        ↓
  我们只定义"怎么传"          企业决定"传什么"          AI决定"怎么说"
（协议/安全/频率）           （数据内容完全自由）       （自然语言呈现）
```

**就好比 USB 接口**：我们定义了 USB 的物理形状（协议），你插什么设备都行（U盘/键盘/手机），插上就能用。

### 5.2 企业需要实现的 API 接口

企业只需要在**自己的服务器**上提供一个 POST 接口：

```php
// https://api.customer.com/kefu/order-query
// 这是我们定义的通用查询接口标准

POST /kefu/order-query
Headers:
  Content-Type: application/json
  Authorization: Bearer {我们预配置的密钥}

Body:
{
    "order_no": "ORD20260512001",    // 用户提供的订单号
    "phone": "138****5678",          // 用户提供的手机号（已脱敏）
    "timestamp": 1716543210,         // 当前时间戳
    "sign": "md5(order_no+phone+timestamp+secret)"
}

Response (成功 - 查询到数据):
{
    "code": 0,
    "msg": "ok",
    "data": {
        // ★ 这里企业想返回什么就返回什么
        // 电商例子：
        "status": "已发货",
        "product": "夏季连衣裙",
        "tracking_no": "SF1234567890",
        "estimated_delivery": "2026-05-15",
        
        // 酒店例子（同一个接口，不同数据）：
        "status": "已确认",
        "hotel": "西湖大酒店",
        "room_type": "湖景大床房",
        "check_in": "2026-05-20",
        "check_out": "2026-05-22",
        "cloud_key_url": "https://hotel.com/roomkey/abc123",
        
        // 教育例子：
        "status": "已报名",
        "course": "Python进阶班",
        "start_date": "2026-06-01",
        "class_link": "https://edu.com/room/456"
    }
}

Response (失败 - 订单号+手机号不匹配):
{
    "code": 40001,
    "msg": "订单号和手机号不匹配"
}
```

**简单来说：企业决定 `data` 里放什么，我们完全不限制。**

### 5.3 verify.php 的工作流程

```
用户: "我的订单到哪了？"
    ↓
AI引导提供订单号+手机号
    ↓
用户: "订单号ORD123，手机13812345678"
    ↓
                    ┌────────────────────────────┐
                    │     verify.php 验证网关      │
                    │                             │
                    │ 1. 频率检查（1分钟3次）       │
                    │ 2. 脱敏手机号 → 138****5678  │
                    │ 3. 调用企业API：             │
                    │    POST https://企业域名/     │
                    │         kefu/order-query    │
                    │    Body: {order_no, phone}  │
                    │                             │
                    │ 4. 企业API返回：              │
                    │    {code:0, data:{           │
                    │      status:"已发货",        │
                    │      product:"连衣裙",       │
                    │      tracking_no:"SF123"     │
                    │    }}                       │
                    │                             │
                    │ 5. 敏感字段脱敏（若有）        │
                    │ 6. 原始data传给chat.php      │
                    └──────────┬─────────────────┘
                               ↓
                    ┌────────────────────────────┐
                    │     chat.php + PromptEngine  │
                    │                             │
                    │ system prompt 中有指令：      │
                    │ "以下是企业系统返回的查询结果，  │
                    │  请用你的语气自然告诉客户"     │
                    │                             │
                    │ AI 读到 data 里的内容：       │
                    │   {status:"已发货",product:"连衣裙"...}
                    │                             │
                    │ AI 自然回复：                │
                    │  "亲~ 查到您的【连衣裙】       │
                    │   已经发货啦，顺丰SF1234567890│
                    │   预计明天到您手上哦~ 😊"     │
                    └────────────────────────────┘
```

### 5.4 为什么这个方案好？

| 场景 | 企业 API 返回的 data | AI 呈现给客户 |
|------|-------------------|--------------|
| **电商** | `{status:"已发货", product:"连衣裙", tracking_no:"SF123"}` | "亲，您的连衣裙已经发货啦，顺丰单号SF123~" |
| **酒店** | `{status:"已确认", hotel:"西湖大酒店", room_type:"湖景房", cloud_key_url:"..."}` | "王先生，您5月20日西湖大酒店的湖景房已确认，点击链接领取云房卡~" |
| **教育** | `{status:"已报名", course:"Python班", start_date:"6月1日", class_link:"..."}` | "您的Python进阶班已报名成功，6月1日开课，点击链接进入教室~" |
| **物流** | `{status:"运输中", location:"杭州分拣中心", estimate:"明天到达"}` | "包裹目前在杭州分拣中心，预计明天送到您手上~" |
| **售后** | `{status:"退款中", amount:"299元",预计:"3个工作日到账"}` | "您的299元退款正在处理中，预计3个工作日到账~" |

### 5.5 企业接入成本

企业只需要在自己的服务器上写一个 PHP 文件：

```php
<?php
// customer.com/kefu/order-query.php
// 这是企业自己实现的接口

$apiKey = '预先配置的密钥';
$input = json_decode(file_get_contents('php://input'), true);

if ($input['order_no'] === 'ORD123' && $input['phone'] === '138****5678') {
    echo json_encode([
        'code' => 0,
        'msg' => 'ok',
        'data' => [
            'status' => '已发货',
            'product' => '夏季连衣裙',
            'tracking_no' => 'SF1234567890',
            'estimated_delivery' => '2026-05-15'
        ]
    ]);
} else {
    echo json_encode(['code' => 40001, 'msg' => '订单号和手机号不匹配']);
}
```

**对企业的要求只有一条**：按我们定义的 `{code, msg, data}` 格式返回数据。`data` 里放什么完全自由。

企业管理员在后台设置：


点击「测试连接」自动验证：
1. 能否连通

### 5.7 安全补充

```
我们的系统                             企业的API
┌──────────────┐                   ┌──────────────┐
│ verify.php    │ ──HTTPS加密──→    │ order-query  │
│ ① 频率限制    │                   │ ① 验证签名    │
│ ② 脱敏手机号  │ ←──返回data────  │ ② 查询数据库   │
│ ③ 日志记录    │                   │ ③ 返回结果    │
│ ④ 数据不落盘  │                   │              │
└──────────────┘                   └──────────────┘

安全措施：
1. HTTPS 强制（数据加密传输）
2. API 密钥验证（预配置，定期轮换）
3. 签名验证（防重放攻击）
4. 企业API返回的原始数据不存库，用完即弃
5. AI 只拿到脱敏后的有限信息
```

## 八、部署流程

### 给新客户部署（10分钟）

```bash
# 购买VPS后，在VPS上安装宝塔
# SSH登录VPS，执行：

git clone https://github.com/你的账号/kefu.git /var/www/kefu

# 2. 一键部署
cd /var/www/kefu
chmod +x deploy.sh
./deploy.sh \
  --domain=kefu.customer.com \     # 客户域名
  --ssl-email=admin@customer.com \ # SSL证书邮箱
  --db-password=SecurePass123 \    # 数据库密码
  --admin-password=Admin888         # 管理后台密码

# 3. ✅ 完成，通知客户
echo "部署完成！管理后台：https://kefu.customer.com/admin"
```

## 九、与现有 OC 平台的关系

由于是独立的单租户 VPS 部署，**客服系统和 OC 平台完全解耦**：

| <br /> | Soulmix OC 平台      | 客服系统                 |
| ------ | ------------------ | -------------------- |
| 部署     | soulmix.app（你的VPS） | kefu.客户域名.com（客户VPS） |
| 代码     | 现有代码不变             | 从现有代码改造，独立仓库         |
| 数据库    | 现有数据库              | 全新独立数据库              |
| 用户     | OC创作者/粉丝           | 企业管理员/普通客户           |
| 关系     | 母项目                | 子项目（fork改造）          |

改造策略：

1. **fork 现有仓库** 为独立仓库 `ai-kefu`
2. 在 `ai-kefu` 中进行改造开发
3. 保留可复用的核心模块（PromptEngine、auth、callAI等）
4. 去掉 OC 专属功能（角色广场、创作者中心、订阅兑换等）
