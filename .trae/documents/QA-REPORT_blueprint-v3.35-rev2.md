## 二、三处重点复查

### a. §5.2 消息序列表 vs §5.2.1 降级表：自洽 ✅
两条规则对象不同，不打架：**房卡原因**——启用场景一律并入 M1（不再独立一条）；**间数引导**——启用场景优先独立、超预算才并入；未启用场景两者都不动（无 extra → 不进 buildOrderGuideMessages，走今天路径）。逐场景加和复核：未到入住单房 1+1+3=5 ✓、0 图 2 ✓、多房轮 1 ✓、2 卡+视频 5 贴线 ✓、3 卡+视频 6→降级① 并间数引导→5 ✓、指引拆 2 条+图 2 = 5 ✓。无 >5 残留。

### b. Pipeline(:115 前) 与通道层(:373) 双点位时序：发现 1 个残留漏洞（D1，必改）
- **新订单号场景：正确。** tryHandle 判 8-30 位数字不匹配候选 → 清 stage → 通道层 matchOrderCandidate（stage=1）落空 → $isOrderMessage 保持 true → 正常查单 ✓。
- **房号命中场景：错位。** tryHandle 先命中并置 **stage=2**；随后 :373 的 matchOrderCandidate 若按 stage=1 查询 → 返回 null → `$isOrderMessage` 仍为 true → **房卡分支照样运行，误发「未找到该渠道订单号」**——恰是 A2 要防的形状。蓝图 §7.5.2 未钉死 matchOrderCandidate 是否依赖 stage=1，两处判定的顺序语义（Pipeline 先消费）没写清。
- **修复（一行）**：通道层加守「`!empty($result['data']['order_guide'])` → 跳过房卡分支」（覆盖一切 pick 命中，不依赖再查表）；或 matchOrderCandidate 明确「不依赖 stage，按候选 JSON 幂等匹配」。
- 实际暴露面小（8 位以上纯数字房号极罕见，§4.2 实测），属低频但必须封死。

### c. 单一守门对视频路径的覆盖：已封死 ✅
视频条件三重：extra 存在（=lead 非空）∧ stage=during ∧ 源文件存在（§5.1 L230 与 §7.6.3 条目 3 一致）。lead 空 → workflow 根本不 set extra → 通道层拿不到 order_guide → 视频不可能被发。unknown stage → lead 强制 ''（§7.1.2）→ 同样无 extra。pick 轮 extra 携带 stage=precheckin，也被 stage=during 条件挡住。无「lead 空但视频发出」的路径。
