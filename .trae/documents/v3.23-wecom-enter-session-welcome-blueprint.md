## 一、需求与结论

**需求**：客户接入微信客服时，若不是直接发订单号，自动发送
「欢迎您咨询柚光民宿ai客服，我是小柚。您想办理自助入住，请发送完整的订单号码」

**结论：可以实现，且不需要自己判断"是不是直接发订单"——企业微信平台已经内置了这个逻辑。**

## 二、接口实测依据（2026-10-13 官方文档核对，非记忆）

### 2.1 事件来源：`enter_session`（不是回调事件，是 sync_msg 返回的消息）

官方《读取消息》文档原文：

> **用户进入会话事件**
> 通过客服链接进入会话，才会触发该事件。**需要注意的是，从客服会话列表的已有会话点击进入，不会触发。**

返回结构：

```json
{"msgtype":"event","event":{
  "event_type":"enter_session",
  "open_kfid":"wkxxx",
  "external_userid":"wmxxx",
  "scene":"...","scene_param":"...",
  "welcome_code":"aaaaaa",
  "wechat_channels":{...}}}
```

`welcome_code` 字段官方原文：

> **如果满足发送欢迎语条件（条件为：用户在过去48小时里未收过欢迎语，且未向客服发过消息），会返回该字段。**

⚠️ **`welcome_code` 有值 = 平台已判定"该发欢迎语"；无值 = 不该发。**
「且未向客服发过消息」这一条**正是苏鸣要的"不是直接发订单"**——
顾客一进来直接甩订单号，微信不会给 `welcome_code`，系统自然什么都不发。
**不需要我们写任何订单号正则判断。**

### 2.2 发送接口：`kf/send_msg_on_event`

官方《发送欢迎语等事件响应消息》文档原文：

- 请求：`POST https://qyapi.weixin.qq.com/cgi-bin/kf/send_msg_on_event?access_token=ACCESS_TOKEN`
- 入参（文本）：

```json
{"code":"<welcome_code>","msgtype":"text","text":{"content":"欢迎咨询"}}
```

| 约束 | 值 |
|---|---|
| code 有效期 | **20 秒** |
| code 可用条数 | **1 条**，**仅可使用一次** |
| content 上限 | 2048 字节 |
| 权限 | 自建应用需配置到「微信客服-可调用接口的应用」 |
| 返回 | `{"errcode":0,"errmsg":"ok","msgid":"..."}` |

## 四、核心设计（幂等优先）

### 4.1 幂等：靠平台，不靠我们

`welcome_code` **仅可使用一次 + 20 秒有效期**。企业微信会自动拒绝重复使用。
cursor 回退导致同一事件被重放时，接口返回 `errcode != 0` → 记日志跳过即可。

**不建去重表、不加锁、不写 DB 状态。** 这是「简单优先」的正解——
平台已经提供了幂等保证，自己再造一套是过度设计。

### 4.2 代码位置与时序

```
handleCallback → kf_msg_or_event → processKfEvent
  → syncMsg() 取回消息数组
  → foreach: 【新增分支】msgtype=event && event_type=enter_session
        ├─ welcome_code 为空 → 记日志跳过（顾客直接发了消息 / 48h 内收过）
        └─ welcome_code 有值 → 立即 sendEnterSessionWelcome()
  → 原有 text/image 分支（不动）
```

⚠️ **必须在循环内同步调用**。`code` 只有 20 秒有效期，不能进队列、不能延后。

### 4.3 文案可配置

存 `platform_config.wecom.welcome_text`，默认值为待确认文案（见第七节 Q2）。
读取用现有 `pcGet($db, 'wecom.welcome_text', '')`，空则回落到代码内默认值。
读取失败不阻断——欢迎语发不出去不应影响正常对话。

### 4.4 ⚠️ 实现陷阱：external_userid 的层级不同（审计发现，遗漏必静默失效）

官方 `enter_session` 结构里，`external_userid` 和 `open_kfid` **嵌套在 `event` 内**：

```json
{"msgtype":"event","event":{"event_type":"enter_session","external_userid":"wmxxx","open_kfid":"wkxxx","welcome_code":"..."}}
```

而现有代码 `api/wecom_kf.php:271` 取的是**顶层**字段：

```php
$from = $msg['external_userid'] ?? '';   // ← event 类型消息这里必然取不到
```

若照抄现有写法，`$from` 恒为空 → **新分支会被下一行 `empty($from)` 的 `continue` 直接跳过**，
表现为"代码上线了但欢迎语永远不发"，且不报任何错。

**正确取值**（新分支内必须这样取）：

```php
$evt       = $msg['event'] ?? [];
$eventType = (string)($evt['event_type'] ?? '');
$from      = (string)($evt['external_userid'] ?? '');   // 嵌套路径
$welcome   = (string)($evt['welcome_code'] ?? '');
$kfId      = (string)($evt['open_kfid'] ?? $useOpenKfId);  // 嵌套路径
```

并且新分支**必须写在 `wecom_kf.php:273` 那个 `continue` 之前**，否则根本进不去。

## 五、已知限制（必须让苏鸣知道）

| # | 限制 | 官方依据 | 影响 |
|---|---|---|---|
| **L1** | **老客户从会话列表点进已有会话，不触发 `enter_session`** | 「从客服会话列表的已有会话点击进入，不会触发」 | ⚠️ **本需求最大短板**：客人第二次来查订单，从微信会话列表点进来**收不到引导语**。只能靠首次接入那一次 |
| **L2** | 48 小时内收过欢迎语不再发 | welcome_code 生成条件 | 复访客人不重复打扰，符合预期 |
| **L3** | code 20 秒失效 | 接口文档 | 循环内同步调用即可规避 |
| **L4** | 依赖应用的「可调用接口」配置 | 权限说明 | 若未配置，接口返回权限错误，**日志可见，不影响其他功能** |

**L1 是产品层面的取舍，不是 bug。** 若苏鸣要求"每次进来都发"，平台能力做不到，需要另想办法（例如每次发消息都判断是否首轮）。

## 八、备选方案（若 Q1 选"不接受"）

**方案 B：每次顾客发消息时判断"是否本会话首轮"**
- 在 `ChatPipeline` 之前查 `chat_logs`，若该 `session_id` 无历史记录 → 先发引导语
- 优点：老客户从任何入口进来，只要开口就一定收到引导
- 缺点：脱离 `welcome_code` 机制，需自建幂等（查 chat_logs 即天然幂等）；引导语与 AI 首答的衔接需处理（要不要等 AI 答完再发）
- 成本：中等，需另出蓝图

**方案 C：什么都不做**
- 维持现状，顾客开口才由 AI 应答
- 成本：零
