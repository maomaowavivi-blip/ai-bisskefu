## 二、修复方案

### 修复 1:IntentRouter 补 PreSalesWorkflow case

**文件**:`api/IntentRouter.php`

**改法**:在 switch 里加 `PreSalesWorkflow` case(REFUND_QUERY 复用 KnowledgeWorkflow,已有 case 覆盖):

```php
case 'PreSalesWorkflow':
    $workflow = new PreSalesWorkflow($db, $config, $intentCtx, $sessionState, $sessionId, $visitorHash, $ip);
    break;
```

**注意**:REFUND_QUERY 的 map 值是 `'KnowledgeWorkflow'`,switch 已有 `case 'KnowledgeWorkflow'`,所以 REFUND_QUERY 实际能走对。只需补 PreSalesWorkflow。

### 修复 2:统一品牌名"宿家/橙途" → "柚光"

**文件清单**(grep 已确认):
- `api/KnowledgeBaseSeed.php`(12 处 "宿家民宿" → "柚光民宿")
- `api/Workflow/PreSalesWorkflow.php`(1 处)
- `api/PromptEngine.php`(1 处默认 brand)
- `api/wecom_kf_roomcard_v37.php`(2 处 "宿家云房卡" → "柚光云房卡")

**注意**:KnowledgeBaseSeed 是"种子"数据,改了代码后**需要重新跑 rebuild 或 SQL 同步到 DB**(线上线下同步铁律)。

### 修复 3:web 端订单查询改 channelOrder

**文件**:`api/Workflow/OrderQueryWorkflow.php`

**改法**:把 `callGateway('query_order')` 换成直接调 channelOrder(复用 wecom_kf_roomcard_v37.php 的 getRoomCard 逻辑)。但 OrderQueryWorkflow 走的是 ChatPipeline(web 端),它返回的是"订单信息"而非"云房卡 link"。

**简化方案**:OrderQueryWorkflow 目前返回"订单查询功能暂未上线"兜底。v3.7 的云房卡 link 发送是 wecom_kf.php 专属逻辑(微信渠道)。web 端订单查询可以:
- 选项 A:也走 channelOrder,返回文本订单信息(入住/离店/房型)
- 选项 B:保持现状(web 端不是主战场,微信客服才是)

**建议选 B**(web 端暂不动,避免扩大改动),本轮聚焦 P0。

### 修复 4:凭证话术更新

**文件**:`api/sidecar/SidecarIntent.php` 的 `yunfangkaCredentialReply()`

**改法**:
```php
return 'WiFi密码、门锁密码、在线交押金及公安刷脸核验，请在云房卡中查看。请直接发送您的订单号，我会为您推送云房卡～';
```

### 修复 5:UnknownWorkflow 用轻量 prompt(学 SmallTalk)

**文件**:`api/Workflow/UnknownWorkflow.php`

**改法**:把 `buildMessages(... kbItems=[] ...)` 换成轻量 prompt(参考 SmallTalkWorkflow),让 LLM 能真正生成兜底话术,而不是永远回 fallback。
