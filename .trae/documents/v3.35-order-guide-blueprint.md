## 1. 目标与非目标

### 目标
客人在微信客服发订单号后，按其处在订单生命周期的哪个阶段，给出不同的信息：

| 阶段 | 新增内容 |
|---|---|
| 未到入住（今天 < 入住日） | 可编辑引导文字 + 中台已维护的入住指引（文字合并为 1 条 + 图片逐条，≤3 张） |
| 入住期间（入住日 ≤ 今天 ≤ 离店日） | 可编辑引导文字 + 云房卡使用指引视频（发卡之后） |
| 退房后（今天 > 离店日） | 可编辑引导文字 |

### 非目标
- 不改中台（`center.youguang8488.com`）任何代码与数据。
- 不改云房卡生成逻辑与话术（仍以中台为准，AGENTS.md §17）。
- 不发定位消息（`lng/lat` 不使用）。
- 不清洗、不改写、不推断中台指引文案（一个字都不改）。
- 不做「指路」内容生产——中台写什么发什么，缺内容由运营补。
- 不修企微回调 20/min 限流旧债（qa C4）。

## 3. 硬约束（官方文档原文 + 生产实测，2026-11-27）

### 3.1 企微微信客服下发条数：每轮 ≤5 条（官方）

`https://developer.work.weixin.qq.com/document/path/94677`《发送消息》最后更新 2026/02/27，
请求地址 `https://qyapi.weixin.qq.com/cgi-bin/kf/send_msg`（**正是本项目在用的端点**，`api/wecom_kf.php:667/696/742/782`）。

> 注意仅当微信客户在主动发送消息给客服后的48小时内，企业可发送消息给客户，最多可发送5条消息；若用户继续发送消息，企业可再次下发消息。

| 用户动作 | 允许下发条数限制 | 下发时限 |
|---|---|---|
| 用户发送消息 | 5条 | 48 小时 |

- 1 条消息 = 1 次 `kf/send_msg` 调用（text / image / link / miniprogram / video 各算 1 条）。
- 客人每发一条新消息，额度刷新为 5 条 → C4 的「问是哪一间」天然带来下一轮额度。

### 3.2 媒体素材规则（官方）

`https://developer.work.weixin.qq.com/document/path/90253`《上传临时素材》最后更新 2024/07/22。

> 素材上传得到media_id，该media_id仅三天内有效
> media_id 媒体文件上传后获取的唯一标识，3天内有效
> 上传的媒体文件限制：所有文件size必须大于5个字节；图片（image）：10MB，支持JPG,PNG格式；语音（voice）：2MB…仅支持AMR格式；视频（video）：10MB，支持MP4格式；普通文件（file）：20MB

- `kf/send_msg` 的 `image` 与 `video` 请求体**都只有 `media_id`**（video 无 title/description 字段）。
- media_id 3 天过期 → **不能长期缓存复用**；必须保留源文件，发送前重新 `media/upload`。
- 不存在永久素材；`media/uploadimg` 的永久 URL 不能填进 `image.media_id`。
- 视频硬上限 10MB（MP4），超限由服务端 ffmpeg 压缩。

### 3.3 中台限流：已取消（生产实测）

生产机复测：连续 **130 次** `s4e3a9` 请求，**130 成功 / 0 失败，耗时 18.1s**。
→ 指引缓存从「必须」降为**可选优化**，**本期不做**（一次中台调用实测 <150ms）。

### 3.3.1 中台本地可直调（与交接文档描述不同）

2026-11-27 开发机实测直调成功（真实房源 `guide_checkin_json` 正常返回），本地 `chat.php` 查单也拿到真实订单信息。
→ **本地开发直接用真实中台数据联调，不需要 mock/fixture**。
→ 本地与生产的差异只剩：**时区**（生产 PHP=UTC/MySQL=CST）与**企微媒体发送**（只能在生产验）。

### 3.4 生产时区：PHP=UTC，MySQL=CST

实测 `date.timezone=UTC`、`php_now=02:42`、`MySQL now=10:42`。
→ **时段判定一律锚 MySQL `CURDATE()`**（§7.1.1），禁止 PHP `date()`。不得为此改全局（AGENTS.md §15）。

### 3.5 配置读写

- 读：`pcGet($db, $key, '')` 直查 DB（禁 `AgentConfig::get()`，AGENTS.md §10）。
- 写：**不能用** `api/agent.php?action=save_config`——它只接受 `agent.` / `plugin.` 前缀的 key（`api/agent.php:82`），其它前缀被静默过滤 → 新增端点（§7.7）。

→ 指引只取 `guide_checkin_json.steps[].{title,text,images}` 白名单，禁止整包 dump 房源 JSON。

### 3.8 生产通道限制（视频上传的硬前置，qa B6）

| 限制 | 默认值 | 处理 |
|---|---|---|
| nginx `client_max_body_size` | **生产实测已是 server 级 `50m`**（`/etc/nginx/conf.d/aibisskefu.conf:212`） | **nginx 侧无需改动**。不要再往 admin location 加——子 location 管不到 `/api/verify.php`，加了也白加 |
| php-fpm `upload_max_filesize` / `post_max_size` | **生产实测 `/etc/php.ini:855` `upload_max_filesize=2M` / `:703` `post_max_size=8M`**；`/etc/php-fpm.d/www.conf` 的 `[www]` 段**没有** php_admin_value 覆盖 → fpm 直接继承 php.ini → **10MB 视频必被拒（真拦路虎）** | 在 `/etc/php-fpm.d/www.conf` 的 `[www]` 段加 `php_admin_value[upload_max_filesize] = 12M` 与 `php_admin_value[post_max_size] = 13M` → `systemctl reload php-fpm`。**只改 fpm pool，不改 /etc/php.ini**（CLI 保持 2M，影响面最小） |
| 企微视频素材 | 10MB MP4 | 后台上传时即校验 |
| 上传目录属主 | 生产 fpm 以 **`apache`** 用户跑（`/etc/php-fpm.d/www.conf:24-26`）；`/www/wwwroot/aibisskefu/uploads` 已是 `apache:apache` | 新建 `uploads/guide/` 必须 `mkdir -p` + `chown apache:apache`（+ 目录权限 755），否则 fpm 写不进去 |

## 5. 消息编排规范

### 5.1 守门：单一守门点（qa B1）

**唯一开关 = 该场景的引导文字是否非空。**

```
$lead = pcGet($db, "order_reply.text.$stageKey", '');   // stageKey ∈ {precheckin,during,after}
if ($lead === '') {
    // 不设置任何 extra，不拼任何附加内容 → 全渠道行为与今天逐字一致
} else {
    $result = $result->withExtra(['order_guide' => [...]]);
}
```

- **workflow 端是唯一守门点**：`lead` 为空 → **根本不 `set extra`** → `ReplyRenderer` 的 `!empty` 判断天然不触发 → API 响应与 v3.34.1 **逐字节一致**。
- 通道层不再二次判 `lead`（只判 `extra` 是否存在），避免两处判定不一致。
- 视频发送条件 = `extra` 存在（= lead 非空）**且** stage=during **且** 视频源文件存在。
- 指引发送条件 = `extra` 存在 **且** stage=precheckin。
- → 「三段全空 → 不发引导文字、不发指引、不发视频」，与今天完全一致。

### 5.2.1 预算公式与降级（qa A1）

```
total = 1(M1) + cardCount(卡) + [间数引导] + [指引文字] + [视频] + 图数
```

**降级优先级（依次尝试，直到 total ≤ 5）**：

| 顺序 | 动作 | 说明 |
|---|---|---|
| **0** | **管家模式**（§5.2.4） | **只在「卡本身装不下」时触发**（cardCount ≥ 5，即 M1 占 1 条后卡只剩 4 条额度）→ 不发卡，改发管家提示。**房卡不可降级**，所以这是唯一出路 |
| 1 | 「间数引导」并入 M1 末尾 | 省 1 条；仅在启用场景发生（未启用场景保持今天的样子） |
| 2 | 删最后一张图片 | 图是最不重要的（30% 房源无图）；3→2→1→0 |
| 3 | 放弃视频 | 记日志 `video skipped: message budget` |
| 4 | 指引文字拆条 / 截断 | 拆条优先（§5.2.3：>600 字拆 2 条并把图片上限同步降到 2）；仍超预算则截断到 600 字。极端兜底（steps 最多 7 步、每步几十字，>1200 字几乎不可能） |

> ⚠️ 管家模式**不在**「卡装得下」的路径上：4 卡 = M1(1) + 卡(4) = 5 条，加视频 6 → 降级③弃视频 → 5 条，**仍然照常发卡**，不进管家模式。

**不降级**：订单信息、房卡（房卡是核心交付）、已发出的历史消息。

### 5.2.2 「间数引导」的归属（qa A1 连带）

- 未启用场景：**保持今天的独立一条**（安全垫，不能动）。
- 启用场景：优先独立保留（与今天观感一致）；超预算时才并入 M1。

### 5.2.3 文本长度规则（qa B4）

| 位置 | 规则 |
|---|---|
| 后台保存 lead | 校验 ≤200 字，超出**拒绝保存**并提示 |
| M1 | `lead(≤200) + 订单信息(~80) + 房卡原因(中台 msg)` 可能超 600 → 超了就把**房卡原因部分**截到 `600 - len(lead+订单信息) - 10` 字（房卡原因来自中台，截断只影响尾巴） |
| 指引文字 M2 | 所有 step 的 `title`+`text` 用 `\n` 拼接（原文不改）。>600 字 → **拆成 2 条**并把图片上限同步降到 2（保证总条数 ≤5）；>1200 字 → 截断到 1200 并记日志 |
| 通道层 | 新拼的消息不经 `wecom_kf.php:362` 的 `mb_substr(600)`，**必须自己截** |

### 5.2.4 管家模式（cardCount ≥ 5，房间太多发不完时）

**触发条件（唯一）**：`cardCount >= 5`。

### 5.3 失败与降级矩阵

| 故障 | 行为 |
|---|---|
| 中台订单查不到 | 维持现状 `ORDER_NOT_FOUND_REPLY`，不动 |
| 中台房源查不到（room_ids 为空 / 房源缺失） | 跳过指引，只发 M1，**不报错、不打断** |
| 中台指引为空（steps=[]） | 不发指引文字、不发图片，只发 M1，**不说「暂无」** |
| COS 图片下载失败 / 企微 uploadMedia 失败 | 跳过该张，**继续发后面的**，文字照常送达，不阻断 |
| 企微 send_msg 失败 | 记日志，继续下一条；全部失败才标记本轮未处理（等微信重试） |
| 视频源文件缺失 | 不发视频，其余完全正常 |
| 视频 media_id 失效（40007/40008） | 删缓存 → 重新 upload → 重发一次；仍失败则跳过视频 |
| **单轮媒体 IO 超时（qa B5 / S3）** | **图片**单轮预算 **20s**（下载 5s、图片上传 15s）；**视频**单独 **30s**（视频上传单独计时，不占图片的 20s）。超预算放弃剩余媒体，文字照发 |
| 新表不存在（发布时序） | `hasPending/match` 内部全 catch → `return null`（fail-open，不影响客服） |

### 5.4 多房选房状态机

```sql
CREATE TABLE IF NOT EXISTS `order_guide_sessions` (
  `session_id`      varchar(64) NOT NULL,
  `order_no`        varchar(64) NOT NULL DEFAULT '',
  `stage`           tinyint NOT NULL DEFAULT 0 COMMENT '0=idle 1=wait_room_pick 2=bound',
  `attempts`        tinyint NOT NULL DEFAULT 0 COMMENT '连续不匹配次数',
  `room_candidates` mediumtext NULL COMMENT '候选 JSON [{baoyu_room_no,room_code,display_name}]',
  `expires_at`      datetime NULL,
  `created_at`      datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`      datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`session_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='v3.35 订单指引多房选房会话';
```

- **TTL = 2 小时**（qa A3：房间流是 30 分钟，24 小时太长）。写入用 SQL：`expires_at = NOW() + INTERVAL 2 HOUR`。
- 读取/判过期**一律 SQL**：`WHERE session_id=? AND stage=1 AND expires_at > NOW()`（**不用 PHP `strtotime`/`time()`**，生产 PHP=UTC 会差 8h，qa B10）。
- 写入时机：**统一在 workflow 侧写**（`OrderQueryWorkflow`：`lead` 非空 && stage=precheckin && 多房 → 写 `stage=1` + 候选 JSON），
  **通道层不写**（只在通道层写 → H5 渠道永远进不了选房；两处写会双写打架）。
  写入用 SQL：`expires_at = NOW() + INTERVAL 2 HOUR`。
- **不吞消息原则（qa A3）**：stage=1 期间，**只有能匹配候选的消息才走选房流程**；不匹配的消息一律走正常流程（不追问、不拦截）。
- `attempts`：不匹配时 +1；≥2 时清 stage（放弃选房，走正常流程）。仅作记录与自愈，不作为拦截依据。

**逃生门（stage=1 期间，遇到以下消息立即清 stage 并走正常流程）**：
- 转人工关键词（`HandoffTriggers::matchKeyword()` 命中）
- 含 `order_query:` / 「订单」/「查单」
- 8-30 位数字且**不匹配**任何候选房号 → 视为**新订单号** → 清 stage，正常查单
- 「退出」「不用了」等**明确退出词**
  （⚠️ P2-9：**不要**把「谢谢」当退出词——`SidecarIntent::isFlowExitMessage()`（`api/sidecar/SidecarIntent.php:54-59`）
  只认「查订单/转人工」，把客套话当退出会在客人道谢时打断选房）

### 5.4.1 选房匹配伪码（qa B9 / C2）

```
normalize(text):
  ①-⑩ → 1-10（mb 归一化）；trim；去空白

candidates = [ {seq:1, baoyu_room_no, room_code, display_name}, ... ]   // 字段名与 OrderRoomMapper::mapOrderData() 产出一致

match(text):
  t = normalize(text)
  if t 命中任意候选的 seq（纯数字且 1..N）        → 返回该候选
  if t 命中任意候选的 room_code（完全相等）        → 返回该候选
  if t 是纯数字且全等某候选的 baoyu_room_no（6-9 位）→ 返回该候选
      ⚠️ 必须排在「新订单号」判定之前：测试房 baoyu_room_no=123456789 本身就是 9 位数字，
         先按 8-30 位判新订单号会把客人回房号误判成新订单（qa 验收 D7 缺口，已修）
  if t 与 room_code / display_name 存在**双向包含**（t 包含 code，或 code 包含 t）:
      较短一方长度 < 2 → 不匹配（避免 t="2" 命中所有含 2 的房号）→ 继续下一条规则
      命中数 == 1（**按候选去重计数**：同一候选的 room_code 与 display_name 命中只算 1，
                   因为 displayName() 已把 room_code 拼进 display_name）→ 返回该候选
      命中数 > 1（如「和德」同时命中和德新天地/和德公馆）→ 判歧义 → **重新发一次选房问句**（带上门店列表）
  if t 含 8-30 位连续数字:
      该数字能匹配某候选 room_code / baoyu_room_no → 返回该候选
      否则                                        → 视为新订单号（清 stage，返回 null）
  否则                                            → 返回 null（正常流程，不追问）
```

**单测必覆盖**：序号、纯数字房号、包含匹配、**「和德」歧义**、新订单号、退出词。

## 7. 代码改动清单

### 7.1 `api/Workflow/OrderQueryWorkflow.php`（改）

**7.1.1 时段判定（纯函数，可本地单测，qa B2/B10）**

```php
/**
 * @param string $today    'Y-m-d'（由调用方用 SELECT CURDATE() 取得）
 * @param string $checkIn  中台 check_in
 * @param string $checkOut 中台 check_out
 * @return string precheckin | during | after | unknown
 */
function orderStage(string $today, string $checkIn, string $checkOut): string
{
    if (!preg_match('/^(\d{4}-\d{2}-\d{2})/', $checkIn,  $mIn))  return 'unknown';
    if (!preg_match('/^(\d{4}-\d{2}-\d{2})/', $checkOut, $mOut)) return 'unknown';
    $ci = $mIn[1]; $co = $mOut[1];
    if ($today <  $ci) return 'precheckin';
    if ($today <= $co) return 'during';
    return 'after';
}
```
- 调用点：`$today = $db->query("SELECT CURDATE() d")->fetch()['d'];`（**锚 MySQL 钟**，禁 PHP `date()`）。
- `unknown`（空/畸形日期）→ **中性**：不拼引导文字、不发指引、不发视频，行为与今天一致。
- 本地单测直接传 `$today` 即可覆盖凌晨 0-8 点边界（不依赖环境时区）。

**7.1.2 引导文字与守门**

**7.1.3 取指引数据（仅在 lead 非空 且 stage=precheckin 时才查中台）**
