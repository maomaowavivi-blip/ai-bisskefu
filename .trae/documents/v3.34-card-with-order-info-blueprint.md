# v3.34 发卡时同步发订单信息 + 发卡事件写入 chat_logs

## 需求（苏鸣 2026-11-20 实测后拍板）

实测订单 123456789（当天入住）发现两处缺口：

1. 微信客服客户**只收到房卡卡片**，没有任何文字——卡片里只有房号，客户不知道这卡对应哪个订单、哪天入住。
2. 房管端聊天记录里**看不到发卡这件事**——发卡是小程序卡片，不进 chat_logs，房管只看到一段订单信息文字，不知道客户已拿到卡。

决策：

1. **订单信息和云房卡一起发**（推倒 v3.32「卡片本身就是回复，不加文本」口径）
2. **补一条发卡事件写入 chat_logs**，房管端可见

## 现状代码事实（已实测读码确认）

- `api/wecom_kf.php:372-471`：`$roomCardSent=true`（卡发出）→ `:468 continue` → `:475` 的 `$replyText` 永远不会发给客户。
- `roomCardTextPlan(true, ...)` 直接返回 `[]`（`wecom_kf_roomcard_v37.php:138`）。
- `chat_logs` 由 `ChatPipeline::writeChatLog`（`ChatPipeline.php:204-244`）写入 user+assistant 两行，channel=`wechat_kf`——所以房管端能看到订单信息文字，但那只是 Pipeline 的口径，不代表真发出去了。
- `openapi_room_chats.php:150-152` 按 session 取 chat_logs **不过滤 role/intent**——新写一条 assistant 事件行即可见。
- 发卡链路已有 `session_order_links` 绑定（写点3），但那是关系绑定，不是可见消息。

## 改动

### 1. `api/wecom_kf_roomcard_v37.php`

- `roomCardTextPlan()` 删掉 `if ($cardSent) return [];` 短路。新语义：**无论发卡成败，订单信息永远第一条**；卡未发出时再补原因/兜底。调用方只在「卡未发出」时传 `$bizMsg`（避免卡成功却因中台瞬时错误误挂兜底句）。
- 新增 `writeRoomCardChatEvent()`：发卡环节结束后（**无论成败**）写一条 assistant 事件进 chat_logs：
  - 成功：`已向客户发送云房卡（房间：10002）`（一单多房逗号拼接）
  - 失败：`云房卡未发送：{中台原因|通用兜底}`
  - 字段对齐 ChatPipeline：session_id/channel=`wechat_kf`/role=`assistant`/workflow=`RoomCardDelivery`/rendered_type=`roomcard`；全 catch，写失败只打日志，不断发卡流程。

### 2. `api/wecom_kf.php:372-471`

- 发卡块重构为单一决策点：
  - 无卡 → `roomCardTextPlan(false, bizMsg, replyText)` 发两条（= v3.32 行为不变）
  - 有卡 → `roomCardTextPlan(true, null, replyText)` 先发订单信息文本（在卡片之前、多卡引导句之前），再逐张发卡
  - 块尾调用 `writeRoomCardChatEvent()` 写事件
- 文本发送失败只记日志，不影响发卡（卡是核心交付）。

### 已知取舍

- 订单信息末尾那句「如需查看云房卡请前往微信客服发送订单号获取」在微信客服场景变冗余（客人已在微信客服、卡就在下面）。本次保留（模板 H5/微信共用，H5 需要这句），要改需按 channel 分叉模板，另拍。
- 有卡但微信发卡全败：客户收到订单信息 + 通用提示（qa P2 修复，保持 v3.32 体验不回退）；该消息已 markMsgProcessed 不重试。重复文本只可能发生在「无卡 + 文本部分失败、微信重试补投」场景，与 v3.32 同型。

## 验证

1. 本机 MAMP php8.3.30 `php -l` 两个改动文件
2. 生产探针：模拟 `roomCardTextPlan(true/false)` 两分支输出
3. 部署后生产回归 `--core` + `--live`
4. 真实验证：入住当天订单在微信客服重发订单号 → 应收到「订单信息文字 + 房卡卡片」，房管端应多出「已向客户发送云房卡（房间：…）」
