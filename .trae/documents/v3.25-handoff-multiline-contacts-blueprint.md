## 三、为什么不能只改配置值（两个必查点）

### 3.1 终检会把多行话术整段吃掉（阻断性）

`api/PromptEngine.php:232-250` `finalizeReply`：无 KB 命中时，回复不含 preserved marker → **整段替换成拒答句**
`api/PromptEngine.php:253-269` `isPreservedReplyWithoutKb`：v3.24 的判定是「回复**整句包含**当前配置话术」

多行话术下整句包含几乎不可能成立：
- LLM 分支模型复述时会改成空格分隔的单行 → 整句匹配失败
- 模型漏一个标点/空格 → 整句匹配失败

→ 一旦失败，用户看到的是「这边暂时没有查到准确信息，建议您联系前台确认。」，**跟转人工毫无关系**。

**修法**：保留判定改为三级，任一命中即保留
1. 回复包含整句话术
2. 回复包含话术的**任意一行**（非空行）
3. 回复包含话术里的**关键数字片段**（≥5 位数字，如手机号 / 客服电话）

第 3 条最关键：模型只要说出任一个号码（哪怕其它部分改写了），就保留。

### 3.2 换行符污染（阻断性）

浏览器 `<textarea>` 的 value 提交上来是 **CRLF**。原样存进 DB / 返回给客户：
- 微信客服纯文本回复里 `\r` 是不可见控制字符，可能显示异常
- `explode("\n", ...)` 切行时会带上残留 `\r`

**修法**：`handoffReply()` 统一归一化 `\r\n` / `\r` → `\n`（前端提交时也归一化一次，双保险）。

### 3.3 prompt 注入用单行折叠版（非阻断，但更稳）

system prompt 里是 `只回复"…"`，引号内含真实换行会破坏指令结构。
→ prompt 注入改用**单行折叠版**（换行 → 空格），**实际发给客户的仍是多行版**。

| 场景 | 用哪版 |
|---|---|
| fast path（客户实际收到） | 多行版 |
| openapi `filterReply` | 多行版 |
| system prompt 注入（给模型看的） | 单行折叠版 |
| 终检保留判定 | 多行版（拆行 / 数字片段） |
