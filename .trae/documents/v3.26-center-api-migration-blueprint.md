## 五、代码改动清单

### 5.1 新增 `api/CenterApi.php`

职责：新中台客户端。凭据从 `platform_config` 读（`pcGet`，**不走 `AgentConfig` 静态缓存**——同 `pcGet` 直查的教训，见 AGENTS.md §10）。

```php
class CenterApi {
    public const RELAY_ORDER   = 's4e1a8';  // 订单查询
    public const RELAY_ROOM    = 's4e3a9';  // 房源
    public const RELAY_NIGHT   = 's4e2a10'; // 间夜列表

    // 内部：拼 URL + GET + 校验 code===1 + 返回 data
    private static function request(PDO $db, string $relay, array $params): ?array;

    /** 按渠道订单号查订单。返回 ['order'=>array, 'paid_amount'=>string] 或 null */
    public static function orderByChannelOrderId(PDO $db, string $channelOrderId): ?array;

    /** 按 baoyu_room_no 查房源。返回首条或 null */
    public static function roomByBaoyuRoomNo(PDO $db, string $baoyuRoomNo): ?array;

    /** 按 room_id 查间夜。返回 list */
    public static function nightsByRoomId(PDO $db, string $roomId): array;
}
```

要点：
- 超时 10s，`CURLOPT_RETURNTRANSFER`
- `code !== 1` → 返回 null + `error_log`
- 密码走 `rawurlencode()`（实测密码为纯字母数字，但不做假设）
- `tenant_id` 从配置读，默认 `1`
- **不缓存**（订单金额必须实时）

## 十、蓝图审计发现（2026-10-22 自审，已回填上文）

审计方式：逐条比对蓝图假设与生产实测，发现 2 处问题。

### 🔴 发现 1：`order_context_cache.room_list` 静默写失败（潜伏 Bug，已修正 §5.2）

| 项 | 实测值 |
|---|---|
| `order_context_cache.room_list` 列类型 | **`varchar(500)`**（NOT NULL） |
| 生产 `sql_mode` | 含 **`STRICT_TRANS_TABLES`** → 超长直接报错 |
| 旧 `channelOrder` 订单对象 JSON 长度 | **1051 字符** → 超限 |
| 新中台订单对象 JSON 长度 | 452 字符（`info_remark` 长文本订单会到 600+，**仍然超限**） |
| 精简载荷 JSON 长度 | **166 字符** ✅ |

**现象**：旧代码 `OrderQueryWorkflow.php:81` 存 `json_encode($orderData)`（整个订单对象）→ MySQL 报 `Data too long` → 被 `catch (\Throwable)` 吞掉 → 只写一行 `cache write failed` 日志 → **订单上下文缓存从未真正写入**。

**证据**：生产 `order_context_cache` 仅 23 行，全部是 2026-05-27 的旧网关基准数据（`room_list` 长度 22）；2026-09-28 / 2026-10-13 的真实查单**没有留下任何缓存行**，而同期 `chat_logs` 里有成功回复。

**修正**：§5.2 改为只写精简载荷（`unit_name / check_in / check_out / room_ids / paid_amount`，约 166 字符）。
`room_list` 的唯一消费方是 `SessionState::loadOrderCache()`（`api/SessionState.php:111`），只做 `json_decode` 塞进 `sessionState['orderCache']['room_list']`，**无人读取其内部字段**，故精简无副作用。

### 🟡 发现 2：`mapOrderData()` 入参形状变化（已在 §5.4 明确）

旧 `callGateway('query_order')` 返回**条目数组**（每项含 `order_info`），新中台返回**单个订单记录**（`room_ids` 逗号分隔）。
`RoomQueryFlow.php:104` 现有写法 `(array)$orderData` 直接透传会拿到 `['order'=>[], 'paid_amount'=>'']` 包装层 → 映射必然失败。
**修正**：`RoomQueryFlow` 传 `$orderResult['order']`；`mapOrderData()` 先按 `room_ids` 分支处理新结构，命中即返回；未命中再走旧结构兼容分支。

### ✅ 审计通过项（无需改动）

- `resolveByIdentifier()` 的 SQL 已覆盖 `baoyu_room_id` 与 `sujia_room_id` 两列 → 新链路零 SQL 改动
- `getDB()` / `getSidecarDB()` 均为进程级单例，`CenterApi` 直接用 `getDB()` 无风险
- `order_context_cache.room_id` 是 `varchar(64)` → 可直接存 `room_ids` 字符串
- `isYunfangkaCardFollowUp()` 只判 `order_context_cache` 是否存在，与载荷形状无关
- `adminGuard()` 在 `api/config.php:164`，新 action 直接复用
- `settings.html:1064` 有顶层 `loadGatewayConfig()` 调用 → 改名时必须同步

## 十一、审计追加：房间流结构性不可达（已修，非本次引入）

### 现象

A/B 实测（生产旧代码 vs 新代码，同一真实订单 `1128140821351313`）：

| 客户输入 | 旧生产代码 | 新版 v3.26 |
|---|---|---|
| 地址怎么走 | 索要订单号 | 索要订单号 |
| **1128140821351313** | 「订单查询成功：房价：¥1940.00」 | **「岭秀学府 广西…商院路18号」**（绑定成功） |
| 有停车场吗 | 仍索要订单号 | **「有停车场。」** |
| 垃圾放哪 | 仍索要订单号 | **返回 tips 文案** |
| 房间有洗衣机吗 | 仍索要订单号 | **「该房间资料未标注洗衣机…」** |

**旧生产代码的房间查询功能（地址/停车/垃圾/设备）100% 不可用**，且与本次迁移无关（迁移前后一致）。

### 根因

1. `IntentClassifier` 第 4 步：任何 `looksLikeOrderNo()` 的消息 → 判为 `ORDER_QUERY`
2. `RoomQueryFlow::handleStep1Order()`：要求消息**本身就是订单号**（`$orderNo = trim($message)`）

两者互斥 → 房间流永远进不了 step=2。
且 `RoomQueryFlow::handle` 只被 `Intent::ROOM_QUERY` → `RoomQueryWorkflow` 调用；`chat.php` 只是 require 该文件，从不调用。

### 设计依据（说明这是补实现，不是新需求）

`.trae/documents/room-query-flow-blueprint.md`：
- §3.1 状态表：`step=1 待订单号 | 等待用户输入：**订单号**`
- 验收清单：「step=1 收到订单号 → 内部 `callGateway(query_order)` 解析（**不展示云房卡**）」

→ 设计本就要求 step=1 能收到订单号继续，**实现缺了路由的会话感知**。

### 修法（最小改动）

| 文件 | 改动 |
|---|---|
| `api/sidecar/SidecarIntent.php` | 新增 `extractOrderNo()`：取消息中最长数字串（≥8 位）；纯字母数字订单号整体返回 |
| `api/IntentClassifier.php` | 新增第 3.5 步：会话处于 `room_session.step===1`（且未过期）+ 消息含订单号 + 消息不含 `order_query:`/订单/查单 → 判 `ROOM_QUERY`，reasoning=`rule:room_flow_continuation` |
| `api/RoomQueryFlow.php` | `handleStep1Order()` 改用 `SidecarIntent::extractOrderNo($message)` 取订单号（兼容「查一下1128…」这类带前后缀回复） |

**边界**：显式 `order_query:` 前缀、客户说「订单/查单」、无活跃房间会话 → 行为完全不变。

## 十二、审计追加：`order_context_cache` 的第二个坑（已修）

## 十四、上线后修正（生产验证阶段发现）

### 修正 1：`save_room_keywords` 畸形请求会静默清空关键词

`getBody()` 对畸形 JSON 返回 `[]`，原写法 `$body['room_keywords'] ?? ''` 会把「参数缺失」当成「显式清空」，
导致一次畸形请求就把 `gateway.room_keywords` 写成空串（房间意图全部失灵）。

改为 `array_key_exists('room_keywords', $body)` 区分二者：参数缺失 → `fail('参数不完整')`；显式空串 → 允许（= 只用代码内置基础词表）。

> 事故记录：验证阶段因 shell 引号错误发出过 `{"room_keywords":}`，关键词确实被清空；
> 已从 `agent.routing.sidecar_entry_extra`（同源同内容，304 字节）逐字节恢复，并复核房间意图命中正常。

### 修正 2：同批加固 `save_center_config`

密码留空 = 不改动已存密码（后台每次保存不覆盖真实密码）；`api_url` / `username` 缺失直接 `fail`，不会写坏配置。
