# 项目工作流指南

> 目标：一个人开发也能保证别人随时接上手

---

## 一、Git 分支策略（极简版）

单人开发，只需要两个分支：

```
main         ← 稳定的、已部署的代码
   │
   └── dev   ← 日常开发分支，随时可以push
```

### 日常流程

```bash
# 开始新功能
git checkout dev
# ... 写代码 ...
git add .
git commit -m "feat: 新增验证码发送接口"
git push origin dev

# 确认稳定后合并到 main
git checkout main
git merge dev
git push origin main
```

**规则**：`main` 永远是可部署状态，`dev` 是工作区。

---

## 二、Commit 信息规范

每次 commit 按照这个格式写，**别人看 git log 就知道改了啥**：

```
<类型>: <简短描述>
```

| 类型 | 什么情况用 | 例子 |
|------|-----------|------|
| `feat` | 新功能 | `feat: 新增 SMS 验证码发送接口` |
| `fix` | 修 bug | `fix: 验证码过期时间计算错误` |
| `refactor` | 重构代码（功能不变） | `refactor: 抽取验证逻辑到 verify.php` |
| `docs` | 改文档 | `docs: 补充订单 API 对接说明` |
| `style` | 改样式/格式 | `style: 客服聊天窗移动端适配` |
| `chore` | 杂项（部署脚本等） | `chore: 新增 deploy.sh 一键部署` |

**这个规范的价值**：
- 以后谁用 `git log --oneline` 一看就知道整个项目进化史
- 知道每个改动是"加功能"还是"修问题"

## 三、项目必须有的几个文件

### 1. README.md（项目的门面）

新来的人第一个看的就是它。必须包含：

```
项目名 - 一句话说明
├── 项目结构（目录树）
├── 快速开始（怎么跑起来）
│   ├── 环境要求
│   └── 步骤 1/2/3
├── 部署（怎么上线）
├── API 对接（企业需要做什么）
└── 相关文档索引
```

### 2. .gitignore（防手滑）

PHP 项目最少要忽略的：

```
.env
node_modules/
.DS_Store
*.log
uploads/*
!uploads/.gitkeep
```

### 3. sql/init.sql（数据库真相源）

所有表结构都在这一个 SQL 文件里，**不要手动改数据库**。改结构就改这个文件，重跑就完事。

### 4. CHANGELOG.md（方便交接时回顾）

每次发布新版本，简单记一笔：

```markdown
## v1.0.0 - 2026-05-12
### Added
- 吉祥物人设配置后台
- 知识库 CRUD 接口
- SMS 验证码验证流程
- 企业订单 API 适配器
```

## 四、技术决策记录（最容易漏的东西）

**这是整个项目最重要的文件**。为什么？因为代码只告诉你"做了什么"，不告诉你"为什么这么做"。

换人最怕的就是："这代码为什么要这么写？不敢改..."

解决办法：每次做一个有争议的决定，就记一笔。

```markdown
# 技术决策记录 (TDR - Technical Decision Records)

## 2026-05-12：不做用户记忆/CRM
- **背景**：最初设计了访客身份识别和记忆系统
- **决策**：全部砍掉
- **原因**：电商/酒旅行业只能通过"订单号+验证码"核验身份，
  口头说手机号不能证明身份。做了记忆反而有隐私风险。
- **替代方案**：每次查询独立验证，查完即清

## 2026-05-12：单租户独立部署
- **背景**：最初想做成 SaaS 多租户
- **决策**：改为每个客户独立 VPS 部署
- **原因**：客户对稳定性要求高，SaaS 一出事影响所有客户；
  独立部署故障隔离，客户数据也更安全
- **代价**：部署成本高一些，但有 deploy.sh 脚本化解决
```

**这个文件的价值**：新来的人看完它，就等于你和他在脑子里过了一遍所有关键决策。省掉无数"为什么要这样"的沟通成本。

## 五、文档自动同步（防脱节的关键）

### 问题
改代码很容易，改文档很麻烦。结果就是：文档越来越旧，AI 一看文档和代码对不上，就全乱套了。

### 解决方案

项目根目录下的 `.trae/rules/doc-sync.mdc` 文件维护了一张 **代码→文档映射表**：

```
改 api/verify.php    → 同时更新 customer-service-plan-v2.md 的验证章节
改 api/knowledge.php → 同时更新 customer-service-plan-v2.md 的知识库章节
改 sql/init.sql      → 同时更新 customer-service-plan-v2.md 的数据库章节
```

**当 AI（我）被要求改代码时，我自动会做三件事：**
1. 改代码文件
2. 查映射表，找到受影响的文档
3. 同步更新文档内容

**commit 里同时包含**代码改动和文档更新，永远不会分开。

### 你需要注意的
- 如果你自己手动改了代码（没通过 AI），记得告诉我一声，我来同步更新文档
- 如果改的是纯样式（CSS 颜色/间距），不需要更新文档
- 其他所有改动，都必须文档同步

### 映射文件位置
`.trae/rules/doc-sync.mdc` — AI 会自动读取这个文件，不需要你手动操作。

## 六、API 对接文档

因为我们的系统需要**企业自己实现一个接口**，所以必须有一份清晰的对接文档。

```
企业需要实现的接口
├── POST /kefu/order-query
│   ├── 请求格式（JSON）
│   ├── 响应格式（JSON）
│   ├── 成功示例（电商/酒店/教育）
│   └── 失败示例
├── 安全要求
│   ├── HTTPS 强制
│   ├── API 密钥
│   └── 签名算法
└── 测试方法（curl 命令）
```

这份文档要给客户的程序员看的，要写得够清楚，对方不需要来问你。

## 七、日常开发 SOP

## 上午
1. git pull origin dev（看看有没有人 push 了代码）
2. 查看 TODO 列表，挑一个今天要做的事
3. 开始写代码

## 写代码时
1. 改数据库？→ 改 sql/init.sql
2. 新增 API？→ 在 api/ 下建新文件
3. 改前端？→ 对应的 .html 文件
4. **同步更新文档** → 查 `.trae/rules/doc-sync.mdc` 映射表
5. 每一步改完 git commit（小步提交，别攒一堆）

> 第 4 步如果是我（AI）在帮你改代码，我会自动做。如果你自己手动改的，告诉我一声就行。

## 测试
1. 本地 XAMPP 跑起来
2. 用 curl 测 API
3. 浏览器看页面效果

## 推送部署
1. git push origin dev
2. SSH 到客户 VPS → git pull
3. 浏览器验证
```

## 九、如果有人来接你的班

他拿到项目后，按这个顺序看：

```
第1步：看 README.md → 知道这是个什么项目，怎么跑起来
第2步：看 DECISIONS.md → 知道为什么这么做，避免踩同样的坑
第3步：看 sql/init.sql → 知道数据结构长什么样
第4步：看 api/ 目录下的文件 → 知道 API 怎么工作的
第5步：git log --oneline → 看提交历史，了解开发顺序
第6步：挑一个小任务开始上手
```

全部看完不会超过 2 小时，他就能开始写代码了。
