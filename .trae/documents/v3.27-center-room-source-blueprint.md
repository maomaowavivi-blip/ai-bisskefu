# v3.27 房间资料数据源切到数据中台 蓝图

> 创建：2026-10-22 by 波尼
> 决策人：苏鸣（2026-10-22 明确：**只有数据中台的数据是准确的，以中台为准，不要再去知识库查询；没有填写的就是没有这个设备**）

---

## 一、背景与问题

v3.26 把订单查询切到数据中台后，暴露出房间资料仍走 sidecar 本地知识库的问题：

| 数据源 | 房间数 | 设备/家电 | 交通 | 入住指引 |
|---|---|---|---|---|
| sidecar `sujia_ai_sidecar_dev` | 921 | `ai_room_device_guide` **0 行** | `ai_room_location.location_note` **0 行有值** | 依赖向量块 |
| 数据中台 `s4e3a9` | **1046** | `guide_appliance_json` **409 个有** | `guide_parking_json` **456 个有** | `guide_checkin_json` **751 个有** |

后果（生产实测）：

- 订单 `123456789` 的房源在中台 `id=1374`（万达广场测试，地址/家电/交通俱全），
  但 sidecar 只收录 921 个（`sujia_room_id` 127~1308），**1374 不在其中** → 客户收到「无法匹配该订单对应的房源资料」
- 房源在库的房间，客户问「房间有空调吗」→ 答「该房间资料未标注空调」
  （实际是中台 `guide_appliance_json` 为 null，sidecar 设备表本来就是空的）
- 客户问「附近有地铁吗」→ 落兜底话术（该房间的地铁信息在中台 `guide_parking_json` 里写着）

**根因**：v3.26 的实现把 sidecar 当作房间资料的**唯一来源**，中台只用于「id 换算」这一步，
于是中台已有的房间资料被挡在门外。

---

## 二、目标（苏鸣 2026-10-22 原话落地）

1. 房间资料**一律以数据中台 `s4e3a9` 为准**，不再读 sidecar 知识库
2. **中台没填的字段 = 该房间没有这个东西**，直接明确回答「没有」，不说「未标注」
3. **中台写什么我们就输出什么。中台写错也是中台的事，不关我们的事。**
   → 我们不推断、不修正、不替中台做判断、不用"我们觉得更合理"的值覆盖中台值；
     中台字段自相矛盾时，只输出其中**有信息量的那个**，不自行调和。

### 原则的落地细则

| 场景 | 做法 |
|---|---|
| 中台 `guide_appliance_json` 为 null | 回「该房间没有登记家电设备。」——中台没写=没有 |
| 中台 `items` 里没有"空调" | 回「该房间没有空调。」——中台没写=没有 |
| 中台 `tips` 是 HTML | **只去标签不改字**（`<br>`→换行），文字内容一字不改 |
| 中台 `short_name` 为空 | 显示名用中台的 `community_name` + `room_code`，**不自己编** |
| 中台 `location_address` 为空 | 只输出 `community_name`；两个都空 → 「该房间未登记地址」 |
| 中台 `parking_lot_name` 为空 | 回「该房间没有登记停车场信息。」——中台没写=没有 |
| 中台字段互相矛盾（见 §4.1） | 只输出有信息量的那个字段，**不调和、不二选一推断** |

## 四、数据质量决策（实测数据支撑）

### 4.1 停车：不能用 `has_parking_lot`

全量 1046 房源实测：

| 判定 | 数量 |
|---|---|
| `has_parking_lot = 1` | **4** |
| `parking_lot_name` 非空 | **280** |
| 两者矛盾（名称有但标志为 0） | **277** |
| `park_charge_status = 1` | 3 |

→ `has_parking_lot` 基本没维护。按「中台写什么就输出什么」：
**以 `parking_lot_name`（中台实际填写的信息）为准**，`has_parking_lot` 这个自相矛盾的标志位不采用
——采用它就是我们在替中台做判断。

### 4.2 显示名：`short_name` 大面积为空

`short_name` 空 **811/1046**。显示名规则：
`short_name` 非空则用 `short_name`；否则 `community_name`；再拼 `room_code`。

### 4.3 `tips` 是 HTML

中台 `tips` 是 `<p>…<br>…</p>`，需转纯文本再给客户。

## 五、改动清单

### 5.1 新增 `api/CenterRoom.php`（中台房源读取 + 解析层）

```php
class CenterRoom {
    public static function loadByBaoyuRoomNo(PDO $db, string $no): ?array;  // baoyu_room_no
    public static function loadById(PDO $db, int $id): ?array;              // 中台房源 id
    public static function appliances(array $room): array;   // guide_appliance_json.items[]
    public static function traffic(array $room): array;      // guide_parking_json.steps[]
    public static function checkin(array $room): array;      // guide_checkin_json.steps[]
    public static function photos(array $room): array;       // room_photos_json.photos[]
    public static function tipsText(array $room): string;    // tips → 纯文本
    public static function displayName(array $room): string;
    public static function addressText(array $room): string;
    public static function parkingName(array $room): string;
    public static function parkCharge(array $room): string;
    public static function toPlainText(string $html): string;
}
```

### 5.2 改 `api/sidecar/OrderRoomMapper.php`

- `mapOrderData()`：订单 `room_ids` 逗号拆 → 每个用 `CenterRoom::loadByBaoyuRoomNo()` 查中台
- 候选结构：`room_id`(中台房源 id) / `baoyu_room_no` / `display_name` / `description` / `room_index`
- **删除** `resolveByIdentifier()` / `resolveBySujiaRoomId()` / `fuzzyMatch()` / sidecar 依赖
  （`mapOrderEntry()` 旧结构兼容分支一并删除——旧网关已下线，无人再走）

### 5.3 改 `api/sidecar/RoomQueryService.php`（数据源全换）

- `query()` / `queryBySidecarId()` → 接收中台房源数组
- 地址 / 停车 / 攻略 / 设备 / 入住 五个分支全部改读 `CenterRoom`
- **设备分支**：`items` 为空或不含目标设备 → 明确回「该房间没有空调。」（不再是「未标注」）
- **停用** `SidecarSearch` 向量检索兜底（不再调用；文件保留，`Vectorizer` 仍用其 `embedTexts`）
- **停用** sidecar `ai_query_log` 写入（该表无任何读取方；主链路 `chat_logs` 已有完整审计）

### 5.4 改 `api/RoomQueryFlow.php`

- JSON 键 `sidecar_room_id` → `room_id`（值为中台房源 id）
- DB 列 `room_query_sessions.sidecar_room_id` **沿用不改**（`int unsigned` 兼容中台 id，
  列注释已失真，代码内注明；不做 DDL 迁移，避免高风险操作）
- `bindAndAnswer()` 入参语义改为中台房源 id

### 5.5 不动

- `api/sidecar/SidecarSearch.php` / `ChunkBuilder.php` / `Vectorizer.php`（文件保留）
- `api/sidecar.php`（sidecar 管理接口）
- 后台「Sidecar 房间知识库」卡的重建/向量化按钮（仍可操作，只是不再参与回答）
- `ai_room_access` 门锁/WiFi 密码（凭证类问题走云房卡引导）

## 六、风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| 中台接口不可用 → 房间查询整体不可用 | 🟠 | 超时 10s；失败返回引导话术（联系前台），不卡住会话；订单查询不受影响 |
| 中台 `tips` 含 HTML 标签 | 🟡 | `toPlainText()` 统一清洗 |
| 中台短名大面积为空 | 🟡 | 显示名兜底规则（§4.2） |
| 中台设备数据只有 409/1046 | 🟡 | 按苏鸣规则，中台没填 = 没有；不回落 sidecar |
| 房间候选从 sidecar 切中台后，一单多房的选房卡内容变化 | 🟢 | `room_candidates` 存中台房源信息，格式随代码同步 |
| 老会话 `sidecar_room_id` 存的是 sidecar id | 🟢 | 会话 TTL 30 分钟，旧会话自然过期；`room_id` 查不到中台房源时按未绑定处理 |

**回滚**：`git revert` + scp + php-fpm reload。**无 DB 结构变更、无数据迁移。**

## 九、v3.27.1 修补(2026-10-23 上线实测发现并修)

上线后按 §七 做生产端到端实测,发现 2 个蓝图中已列出、但代码没修完的问题,当场修掉:

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 「附近有地铁吗」落兜底话术 | `RoomQueryFlow::handleStep3FollowUp()` 先判 `isGeneralKbQuestion()`,该函数含「附近」→ 直接回落通用 KB,房间分支根本没执行(而中台 `guide_parking_json` 里写着地铁指引) | 新增 `RoomQueryService::isRoomSpecificQuery()`(地址/交通/停车/攻略/设备/凭证);step=3 先判房间类,非房间类才回落通用 KB |
| 2 | 客户发房号(如 10002)选不了房 | `handleStep2Pick()` 里 `preg_match('/^\d+$/')` 在前,数字一律当**候选序号**,10002 → 第 10002 个候选 → 选房必失败;房号分支只在非数字时才可能命中 | 纯数字先按 `room_code` 精确匹配,匹配不到再回落为候选序号 |
