# v3.15.3 修改蓝图:云房卡闸门放宽(允许带中文/句式)

**日期**:2026-08-18
**作者**:波尼(执行),苏鸣(审核)
**状态**:待审计

---

## 一、根因

**线上 `api/wecom_kf.php:288`** 的云房卡闸门:
```php
$isOrderMessage = preg_match('/^\d{8,30}$/', $trimmedMsg) === 1;
```
要求消息**纯数字 8-30 位**才会触发 A 样式云房卡。

**真人发订单号**几乎都是带中文前缀的句式:
- "你好，我的订单号是123456789"
- "订单号：5035035963841932965"
- "帮我看一下5035035963841932965"

只要消息带中文/标点 → `$isOrderMessage=false` → 走 ChatPipeline → IntentClassifier 判 SMALL_TALK(因为"你好"/"订单号" 等关键词权重高)→ SmallTalkWorkflow LLM 自由发挥 → "您好呀！订单号收到。" → ❌ 无查单、无云房卡。

**线上证据**(8/18 10:49 chat_logs):
| 用户消息 | intent | workflow | 助手回复 |
|---|---|---|---|
| `你好，我的订单号是123456789` | SMALL_TALK | SmallTalkWorkflow | "您好呀！订单号收到。" ❌ |
| `5035035963841932965`(纯数字) | ORDER_QUERY | OrderQueryWorkflow | 订单信息+引导云房卡 ✅ |

闸门正则自 v3.9 沿用至今,v3.15.2 回归测试用的是纯数字订单号,所以一直没暴露这个 bug。

## 二、方案

### 2.1 改造点(单一文件,5 行)

**文件**:`api/wecom_kf.php`

**当前代码**(第 286-299 行附近):
```php
$sessionId = 'wecom_kf_' . substr(sha1($from), 0, 16);
$trimmedMsg = trim($content);
$isOrderMessage = preg_match('/^\d{8,30}$/', $trimmedMsg) === 1;
```

**改造后**:
```php
$sessionId = 'wecom_kf_' . substr(sha1($from), 0, 16);
$trimmedMsg = trim($content);

// v3.15.3:放宽闸门 — 消息中包含 8-30 位数字串即视为订单号
// 优先级:取消息中第一个 8-30 位数字串作为 $orderCandidate
// 长度范围 8-30 足以避开手机号(11 位但不强制)、身份证(18 位)
// 真实订单号是 19 位(5035035963841932965),闸门仍接受
if (preg_match('/\b(\d{8,30})\b/', $trimmedMsg, $mOrder) === 1) {
    $isOrderMessage = true;
    $orderCandidate  = $mOrder[1];
} else {
    $isOrderMessage = false;
    $orderCandidate  = '';
}
```

**第 338 行** buildRoomCardDelivery 入参改用 `$orderCandidate`:
```php
$delivery = buildRoomCardDelivery($db, $orderCandidate);
```

### 2.2 不动的地方

- ChatPipeline / IntentClassifier / OrderQueryWorkflow — 完全不动
- `wecom_kf.php` 第 291-323 行的 ChatPipeline 处理逻辑 — 完全不动(中文消息仍走 LLM 回复,这是预期行为)
- `buildRoomCardDelivery` 内部 — 完全不动(订单不存在自动返 null + 兜底文案,已确认安全)

## 三、为什么这样改就够了

| 场景 | 旧行为 | 新行为 |
|---|---|---|
| 客户发 `5035035963841932965`(纯数字) | ✅ 发云房卡 | ✅ 发云房卡(走 `$mOrder[1]`) |
| 客户发 `你好，我的订单号是123456789` | ❌ 不发 | ✅ 发(数字串 123456789 → 走房卡) |
| 客户发 `订单号：5035035963841932965` | ❌ 不发 | ✅ 发 |
| 客户发 `你好` | ❌ 不发(无数字串) | ❌ 不发(无数字串) |
| 客户发 `手机号 13800138000` | ❌ 不发 | ⚠️ 会试 — buildRoomCardDelivery 调宿家 API → 订单不存在 → 兜底文案"暂时未能打开云房卡" |

第 5 行场景是苏鸣授权接受的(明确说"不担心,匹配不到订单也是返回订单号错误")。

## 四、风险评估

| 风险 | 等级 | 说明 |
|---|---|---|
| 误把手机号/身份证当订单号 | 低 | 走宿家 API → 失败 → 兜底文案,不泄露任何凭证 |
| 性能影响 | 极低 | 多跑一次 preg_match,可忽略 |
| 多订单号(用户发两个) | 极低 | 取第一个即可,异常时人工兜底 |
| 现有 ORDER_QUERY 路径 | 无影响 | 纯数字消息仍走完整 ChatPipeline + OrderQueryWorkflow,**不**走云房卡闸门(我们没动这一段) |
