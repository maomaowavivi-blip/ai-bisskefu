# v3.30 房管系统「昨日AI聊天」查询接口 — 蓝图

> 2026-11-19 起草。状态：**已审计**（审计修正：写点1 channel 注入方式、写点2 位置细化、回填源3 确认可行、响应 channel 来源）。

## 1. 需求

房管在**自己的管理系统**里点「昨日AI聊天」→ 列出他名下房源**有 AI 客服聊过的对话**（没聊过的不出现）→ 点某条对话 → 展示该客人当天的 AI 聊天记录。

我方只做一个查询接口 + 落定「会话 ↔ 订单」绑定层。订单→房源→房管 的归属计算全在房管系统侧（他们有 PMS 关系）。

**已确认口径（苏鸣 2026-11-19）**：
- 房管系统的订单号与客人报给 AI 的订单号（中台 channel_order_id，携程/美团单号）是同一个号。
- 闲聊没报订单号的会话不需要展示（本来也无法归属）。
- 一次调用返回「对话列表 + 每对话完整消息流」，房管系统点开不再二次请求。

## 3. 方案

### 3.1 新表 `session_order_links`（绑定真身）

不复用 order_context_cache 做查询源：它是 24h TTL 语义 + session 主键 upsert（后查的单会覆盖先查的），未来可能被清理任务掏空。绑定表 append-only。

```sql
CREATE TABLE session_order_links (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  session_id VARCHAR(64) NOT NULL,
  channel VARCHAR(20) NOT NULL DEFAULT '',
  order_no VARCHAR(64) NOT NULL,
  room_no VARCHAR(100) NOT NULL DEFAULT '' COMMENT '逗号分隔房号(来自订单 room_ids)',
  source VARCHAR(20) NOT NULL DEFAULT '' COMMENT 'order_query|room_flow|roomcard|backfill',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_session_order (session_id, order_no),
  KEY idx_order_created (order_no, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

统一写入 helper（新增，放 `api/helpers/session_order_link.php`）：

```php
function linkSessionOrder(PDO $db, string $sessionId, string $orderNo, string $roomNo, string $channel, string $source): void
```

### 3.2 写点（3 处 + 1 行注入，全部 try/catch 隔离）

0. **channel 注入**（`api/ChatPipeline.php:121` 后）：`$intentCtx->slots['channel'] = $channel;`——基类无 channel 字段（审计实测），沿用 slots 传参先例。

   覆盖：H5 查单流 + 微信客服订单号消息（主流量）。
2. **RoomQueryFlow step=1 订单号确认点**（`OrderRoomMapper::mapOrderData()` 返回候选之后、单房/多房分支之前，`RoomQueryFlow.php:110` 附近）：`room_no` 直接取订单 `room_ids` 原始逗号串（候选里也有 `baoyu_room_no` 可拼）。**不能只挂在 step=2 saveState**——单房订单会直接 `bindAndAnswer` 跳过 step2（审计实测）。source='room_flow'。

### 3.3 查询端点：新文件 `api/openapi_room_chats.php`

- `POST`，鉴权块复制 `openapi.php:33-52`（X-API-Key / Bearer + api_keys 查表 + last_used_at）。独立文件，不碰其他集成方在用的 openapi.php 主链路。
- Body：`{"order_nos": ["...", ...], "date": "YYYY-MM-DD"(可选,默认昨天)}`
  - order_nos：必填，数组，1–200 项，每项 trim 后 `^[A-Za-z0-9_\-]{4,64}$`，去重。
  - date：`^20\d{2}-\d{2}-\d{2}$` + `checkdate()` 双重校验，非法（含 2026-02-31 类滑窗值）400。
  - **默认「昨天」取 MySQL 钟**（`SELECT DATE_SUB(CURDATE(), INTERVAL 1 DAY)`）：全仓无 `date_default_timezone_set`，PHP 进程钟可能是 UTC，与 chat_logs 写入钟（DB DEFAULT CURRENT_TIMESTAMP）不同源会差一天；qa 实测强制 PHP=UTC 下默认窗口仍精确命中 DB 昨天。
- 查询：
  1. `SELECT session_id, order_no, room_no, channel FROM session_order_links WHERE order_no IN (...)`
  2. `SELECT ... FROM chat_logs WHERE session_id IN (...) AND created_at >= ? AND created_at < ? ORDER BY session_id, id ASC`（左闭右开整天，服务器时区，与 chat_logs 现网时间一致）
  3. 当天无消息的 session 丢弃。
- 响应（`ok()` 包）：
  ```json
  {"code":0,"data":{"date":"2026-11-18","list":[
    {"order_no":"...","room_no":"10002","session_id":"wecom_kf_x","channel":"wechat_kf",
     "message_count":12,"first_time":"...","last_time":"...",
     "messages":[{"role":"user","content":"...","created_at":"..."}]}
  ]}}
  ```
  - 一个 session 绑多个订单 → 每订单一一条，消息流重复，由房管系统按订单分组。
  - **channel 字段取自 chat_logs 行自身的 channel**，不依赖绑定表（审计定稿）。
  - 每对话 messages 上限 500 条（按时间取最前 500，超限置 `truncated:true`）。
- 不设主动限流：调用频率 = 房管点击频率（每天个位数），IN 列表封顶 200。

### 3.4 回填脚本 `scripts/backfill_session_order_links.php`（幂等）

- 源 1：`order_context_cache WHERE order_no != ''` → source='backfill'，room_no=room_list，channel 由 session_id 前缀映射（`wecom_kf_`→wechat_kf，`openapi_`→api，其余 web）。
- 源 2：`room_query_sessions WHERE order_no != ''` → source='backfill'，room_no 取 room_candidates JSON 里各候选的 `baoyu_room_no` 逗号拼（无 candidates 则留空）。
- 源 3（审计确认）：`chat_logs WHERE intent IN ('ORDER_QUERY')` 行，`JSON_EXTRACT(slots,'$.original_message')` 文本过 `extractOrderCandidate()`（复用 `api/helpers/order_candidate.php`），提出订单号即 link（channel 用行自身值）。三源互补：cache 覆盖成功查单、room 表覆盖房间流、chat_logs 覆盖 cache 写失败/房卡发放但 Pipeline 没成 cache 没写的场景。
- 全部走 `linkSessionOrder()`，输出「新增 N / 跳过 M」。生产跑一次。

## 4. 影响面与回滚

- 写点在消息主链路内，但 helper 全 catch，最坏丢一条绑定不影响客户对话。
- 新表 + 新端点，零侵入现网行为。回滚：DROP TABLE + 删 2 个新文件 + revert 3 个写点文件的 diff。
- 回归必跑：写点动了主链路文件（`--core` 对生产）。

## 5. 验收标准

1. 本地：手工造「订单 A + session + 昨天消息」→ 接口返回该对话完整消息流；换成前天日期 → 不返回；无 key/坏 key → 401/403；order_nos 非法 → 400。
2. 本地真实链路：发「订单 1128148162721995」进 chat 流 → 绑定表出现该 session↔订单行。
3. 回填幂等：跑两遍，第二遍新增 0。
4. `php -l` 全绿；回归 `--core` 无新增失败。
5. 生产 DDL 后 md5 校验一致；php-fpm reload。
